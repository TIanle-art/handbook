## 1. 使用说明

### 1.1 这份文档解决什么问题

团队用 AI 开发后，写代码快了很多，但这些问题不会自动消失：

- 需求没说清楚，AI 很快就做出一个错误的版本。
- 多人和多个 Agent 同时改同一批文件，冲突变多。
- PR 产出的速度超过了人审查的速度。
- 上下文留在个人的聊天记录里，换人或换会话就要重新解释。
- 没人说得清一段代码为什么这样写，出了问题也没人兜底。

这份规范的目标是：**每项工作都有明确的负责人、依据和完成标准，上下文留在仓库里，而不是个人脑子和聊天记录里。**

### 1.2 团队现状和前提

| 项目 | 现状 |
|---|---|
| 团队规模 | 4 到 8 人，一人可以兼任多个角色 |
| 项目类型 | 客户外包和自研产品都有 |
| 代码托管 | 个人 GitHub 账号的免费私有仓库，以后转到免费组织 |
| 任务管理 | GitHub Issues + Projects |
| AI 编码工具 | Claude Code、Cursor、Codex、GitHub Copilot、Kimi Code、OpenCode 等，成员自选 |
| AI 协作层 | Trellis + `AGENTS.md` + 公司 Skill |
| 复杂需求 | OpenSpec |

### 1.3 关于免费 GitHub 的限制

免费计划的私有仓库**没有分支保护**，所有协作者都能直接推送 `main`、合并 PR 和修改 workflow。因此本规范中的很多规则只能靠约定。为了弥补这一点，团队用三层办法：

1. **约定：** 本规范写明谁能做什么。
2. **本地拦截：** Git hook 阻止在 `main` 上提交和直接推送 `main`。
3. **事后检查：** CI 中的 `main` 守卫发现没有经过 PR 或没有批准就进入 `main` 的提交。

此外，生产服务器的登录权限只给维护者，生产密钥不放进 GitHub。即使有人绕过约定，也不能直接改动线上服务。

具体配置见《公司项目脚手架规范》第 4 章和第 6 章。

### 1.4 按团队规模裁剪

| 规模 | 必须保留 | 可以简化 |
|---|---|---|
| 4 至 8 人（当前） | 本文全部流程 | M 级需求的评审可以异步完成 |
| 临时只有 2 至 3 人 | 书面验收标准、PR、CI、互相审查、发布清单、备份 | 会议合并为每周一次 30 分钟同步，角色全部兼任 |
| 超过 8 人 | 本文全部流程 | 按项目分组，每组设技术负责人；评估转到组织并开通 GitHub Team |

## 2. 流程总览

### 2.1 全景图

```text
线索评估 → 业务发现 → 立项 → 需求规格 → 技术方案 → 拆任务排期
                                                    │
    ┌───────────────────────────────────────────────┘
    ▼
  开发循环（每个任务重复一次）
  领取任务 → AI 实现 → 自检 → PR → CI → 人工审查 → 合并
    │
    ▼
  测试环境验证 → 业务验收 → 发布 → 上线观察
    │
    ▼
  运营维护 → 结项复盘 → 经验写回规范和模板
```

### 2.2 阶段与闸门

每个阶段结束都有一道闸门，闸门没过，不进入下一阶段。

| 阶段 | 主负责人 | 核心产出 | 闸门 |
|---|---|---|---|
| 线索评估 | 项目负责人 | 评估记录 | 值得做，主要风险可以接受 |
| 业务发现 | 项目负责人 | 业务发现记录 | 有业务拍板人，第一期范围和成功标准明确 |
| 立项 | 项目负责人 | 项目简报 | 目标、范围和负责人明确；客户项目的关键条款已确认 |
| 需求规格 | 项目负责人、开发者 | Issue、PRD 或 OpenSpec 变更 | 验收标准和非范围已人工确认 |
| 技术方案 | 技术负责人 | 技术方案、ADR、接口草案 | 架构、数据结构和风险已评审 |
| 拆任务排期 | 技术负责人、开发者 | Issue、依赖关系、里程碑 | 每个任务都满足可开工标准 |
| 开发 | 开发者 | 代码、测试、PR | 满足完成标准，CI 和人工审查通过 |
| 测试验收 | 项目负责人 | 测试和验收记录 | 验收标准通过，没有未解决的严重缺陷 |
| 发布 | 技术负责人 | 发布记录 | 健康检查和核心流程验证通过 |
| 结项复盘 | 项目负责人 | 复盘记录、交付物 | 交付物齐全，改进项有负责人 |

### 2.3 十二条基本规则

1. **没有验收标准，不开工。** 再小的任务也要写清怎样才算做完。
2. **每项工作只有一个负责人。** 可以多人参与，但只有一个人对结果负责。
3. **提交者对代码负责。** 无论代码是谁或什么生成的，提交 PR 的人都必须能讲清楚。
4. **AI 不能批准合并。** AI 可以做第一轮审查，批准必须来自人。
5. **`main` 始终可以部署。** 不直接推送 `main`，不合并没有通过 CI 和审查的代码。
6. **上下文写进仓库。** 决定、规格和交接信息不能只留在聊天记录里。
7. **先定接口，再并行。** 多人协作前，先定下接口和数据结构。
8. **并行规模由审查能力决定。** 不由 AI 能写多快决定。
9. **高风险改动必须有回滚方案。** 没想好怎么退回去，就不上线。
10. **同样的错误不犯第二次。** 反复出现的问题写进规范、Skill 或自动检查。
11. **需求只有一个权威来源。** 用了 OpenSpec，其他地方只放链接，不重复写。
12. **工具可以不同，门禁必须相同。** 无论用哪个 Agent，都要通过同样的 CI 和审查。

## 3. 角色与责任

### 3.1 角色说明

| 角色 | 主要职责 | 关键权力 |
|---|---|---|
| 公司负责人 | 资源分配、合同、合规和公司资产 | 决定接不接项目，跨项目协调 |
| 项目负责人 | 对接客户和业务，定目标、范围、优先级和验收标准，跟进度和风险 | 决定做什么、先做什么、是否验收 |
| 业务拍板人 | 回答业务问题，确认规则和验收结果。客户项目通常由客户方指定 | 确认业务规则是否正确 |
| 技术负责人 | 技术方案、架构一致性、L3 审查、发布、故障指挥 | 决定怎么做，可以否决不安全的方案或发布；持有生产服务器权限 |
| 开发者 | 拆解和实现任务，驱动 AI，写测试，自检，跟进 PR，修复自己引入的问题 | 决定任务内的实现细节 |
| 审查者 | 审查需求符合度、设计、安全、测试和可维护性 | 可以要求修改，阻止合并 |
| 模板负责人 | 维护脚手架、规范、公司 Skill、CI 和 AI 工具准入 | 决定什么进入公共模板 |

### 3.2 责任矩阵

R = 执行，A = 最终负责（每项只有一个），C = 征求意见，I = 知会。

| 事项 | 项目负责人 | 技术负责人 | 开发者 | 审查者 | 模板负责人 |
|---|---|---|---|---|---|
| 业务发现和项目简报 | A/R | C | I | | |
| 需求和验收标准 | A/R | C | C | | |
| 技术方案和 ADR | C | A/R | R | C | |
| 任务拆分 | C | A | R | | |
| 代码实现和测试 | I | C | A/R | | |
| PR 审查 | | C | C | A/R | |
| L3 改动审查 | I | A/R | C | C | |
| 业务验收 | A/R | I | C | | |
| 发布和回滚决定 | C | A/R | C | | |
| 故障指挥 | C | A/R | R | | |
| 规范、模板和 Skill | | C | R | C | A/R |
| AI 工具准入 | | A | C | | R |

### 3.3 兼任规则

- 项目负责人和技术负责人可以是同一人，但要有意识地切换视角。
- 作者不能批准自己的 PR，GitHub 也不允许。
- 尽量不让同一个人既实现又独自完成业务验收。人手不够时，至少请另一个人走一遍核心流程。
- 技术负责人、模板负责人和生产服务器权限都要有一名备份，避免一人缺席时流程停摆。

## 4. 按工作类型选择流程

不是每项工作都要走完整流程。先判断类型、规模和风险，再决定流程轻重。

### 4.1 工作类型

| 类型 | 适用情况 | 流程 |
|---|---|---|
| 新项目 | 新客户或新产品 | [第 5 章](#5-项目全流程)完整流程 |
| 功能开发 | 已有项目的新能力 | 从需求规格开始 |
| 缺陷修复 | 行为不符合预期 | Issue → 修复 → PR → 验证 → 发布 |
| 紧急修复 | 线上严重问题 | [第 14 章](#14-线上故障处理)，事后补记录 |
| 技术任务 | 重构、依赖升级、性能优化 | Issue 写明目标和验证方式；风险大时写 ADR |
| 技术探索 | 不确定是否可行 | 限时探索，产出结论，代码默认不合并 |

### 4.2 需求规模

| 规模 | 判断标准 | 需要的文档 | 评审 |
|---|---|---|---|
| S 小 | 不超过 1 个工作日，不改数据结构和接口契约 | Issue | 负责人看过即可 |
| M 中 | 1 到 5 个工作日，涉及接口或多个模块 | 一页 PRD | 项目负责人和技术负责人确认，可以异步 |
| L 大 | 超过 5 个工作日，跨端或涉及架构 | PRD + 技术方案 + ADR | 开评审会 |
| 复杂业务 | 业务规则多、会长期迭代、容易有争议 | OpenSpec 变更 | 业务拍板人和技术负责人确认 |

工作量按**包括审查、测试和验收的总时间**估算，不只估 AI 写代码的时间。

### 4.3 风险级别

| 级别 | 范围 | 审查要求 | 发布要求 |
|---|---|---|---|
| L1 低风险 | 文案、样式、内部工具的小改动 | 1 人审查 | 随常规版本发布 |
| L2 普通 | 普通业务功能 | 1 人审查 + 完整 CI | 测试环境验证后发布 |
| L3 高风险 | 登录、权限、支付、计费、数据删除、数据库迁移、租户隔离、AI 工具权限、CI 和部署脚本、生产配置 | 技术负责人审查 + 回滚方案 | 备份，发布时有人值守，发布后观察 |

规模和风险是两个独立的维度。比如改一行权限判断是 S 规模，但属于 L3 风险。

### 4.4 技术探索的规则

- 提前定好要回答的问题和时间上限，通常不超过 2 个工作日。
- 探索代码放在 `spike/` 分支，默认不合并。
- 产出一份简短结论：是否可行、建议方案、主要风险和工作量估算。
- 决定实施后，按正常流程重新开发，不把探索代码直接带进主分支。

## 5. 项目全流程

### 5.1 线索评估

**负责人：** 项目负责人，技术负责人协助。

**要回答的问题：**

- 客户或用户要解决的真实问题是什么？
- 是否真的需要软件？需要哪种端？桌面和小程序都有额外成本。
- AI 在这个项目中是否必要？模型效果能否达到业务要求？
- 预算和时间是否合理？模型调用的持续成本由谁承担？
- 有没有合规、数据或资质方面的风险？

**闸门：** 决定继续、暂缓或拒绝，并记录原因。

### 5.2 业务发现

需求不清的项目最容易失败。OpenSpec 等工具能把需求记录清楚，但不能替团队想清楚需求；业务不明确时，AI 只会生成一份看起来很完整的错误规格。所以新项目和需求不清的项目，先用 1 到 2 周做业务发现。

**负责人：** 项目负责人。

**步骤：**

1. **指定业务拍板人：** 懂业务、会实际使用产品的人。没有拍板人，不进入正式开发。
2. **收集真实样本：** 真实文件、历史结果、错误案例和现有流程，先脱敏。
3. **跟着用户走一遍：** 记录每一步在做什么、花多长时间、出错有什么后果。
4. **列出不明确的问题：** 每个问题写明由谁回答、何时回答。
5. **缩小第一期范围：** 先做好一个场景，不追求一次覆盖所有场景。
6. **定义成功标准：** 用可以验证的指标，比如关键信息漏提为 0，或准备时间减半。

**产出：** `docs/discovery/` 中的[业务发现记录](#212-业务发现记录)。

**闸门：**

- [ ] 业务拍板人已确定
- [ ] 第一期范围和非范围明确
- [ ] 成功标准可以验证
- [ ] 已有脱敏的真实样本

### 5.3 立项

**负责人：** 项目负责人。

**动作：**

1. 填写[项目简报](#211-项目简报)。
2. 指定项目负责人、技术负责人和业务拍板人。
3. 按《公司项目脚手架规范》第 3 章和第 5 章选择技术组合和后端。
4. 用模板创建仓库，配置协作者、Git hook 和看板，见 [10.9](#109-创建新项目)。
5. 客户项目按 [16.1](#161-立项前确认的条款) 确认合同关键条款。
6. 按 [17.1](#171-数据分级) 填写项目的数据清单。

**闸门：**

- [ ] 目标和成功标准明确
- [ ] 本期范围和非范围明确
- [ ] 负责人已指定
- [ ] 数据和 AI 工具的使用边界明确
- [ ] 第一个里程碑明确

### 5.4 需求规格

**负责人：** 项目负责人定义业务，开发者补充技术细节。

**动作：**

1. 把需求拆成可以单独验收的功能。
2. 按 [4.2](#42-需求规模) 选择文档形式：Issue、PRD 或 OpenSpec。
3. 把模糊的表述改成可以验证的标准，见 [6.2](#62-把需求写到可以验证)。
4. 写明非范围，防止人和 AI 顺手多做。
5. AI 功能额外写明成功标准、不允许出现的结果、失败处理和成本上限。

**闸门：**

- [ ] 业务拍板人确认业务规则
- [ ] 验收标准覆盖正常、错误和权限场景
- [ ] 非范围已写明
- [ ] 待确认问题已关闭，或有明确的负责人和期限

### 5.5 技术方案

**负责人：** 技术负责人或指定的开发者。

**什么时候必须写：** L 级需求、L3 风险改动、新增第三方服务、跨端改动，以及任何难以撤销的决定。

**方案包括：**

- 涉及的模块和调用关系
- 接口和数据结构草案
- 迁移方案和兼容策略
- 错误处理、权限和安全
- AI 调用方式、token 成本估算和评估方法（如适用）
- 备选方案和取舍
- 测试和发布方案
- 风险和回滚方案

AI 可以帮忙起草和找漏洞，比如另开一个 AI 会话专门挑问题，但采用哪个方案由人决定。

**闸门：** 技术负责人批准；重要决定写成 [ADR](#214-adr)。

### 5.6 拆任务与排期

**负责人：** 技术负责人和开发者。

**动作：**

1. 先拆出共享的基础任务：接口契约、数据结构、公共组件。
2. 按模块分配，尽量减少多人改同一批文件。
3. 标明任务依赖，被依赖的任务先做。
4. 估算工作量，给审查、测试和修复留出时间。
5. 建立里程碑，放进 GitHub Projects。

**排期提醒：**

- 不按 AI 写代码的速度排期。需求不清、审查排队和真机验证往往才是主要耗时。
- 小程序审核、证书申请、备案和客户验收都依赖外部，要提前留足时间。
- 每个里程碑都留缓冲，比例根据前几个项目的实际偏差确定。

**闸门：** 第一个里程碑的任务都满足[可开工标准](#72-可开工标准)。

### 5.7 开发

**负责人：** 开发者。

```text
1. 领取任务，确认验收标准
2. 从最新的 main 创建分支或 worktree
3. 新开 AI 会话，加载规范和任务上下文
4. AI 先说明计划，人确认后再实现
5. 小步实现和提交，及时运行检查
6. 人亲自看完整 diff，完成自检
7. 创建 PR，写清改动、验证方式和风险
8. 处理 CI 和审查意见
9. 获得批准后合并，确认测试环境部署成功
```

AI 的用法见[第 8 章](#8-人与-ai-协作)，具体命令见 [10.11](#1011-开发者日常操作)。

**闸门：** 满足[完成标准](#73-完成标准)。

### 5.8 测试与验收

**负责人：** 项目负责人组织，开发者配合。

1. 部署到测试环境。
2. 按验收标准逐条验证，保存结果。
3. 按严重程度记录缺陷，修复后回归验证。
4. 客户项目组织客户验收，取得书面确认。

详见[第 12 章](#12-测试与验收)。

**闸门：** 验收标准全部通过，没有未解决的 S0、S1 缺陷，S2 缺陷有明确决定。

### 5.9 发布

**负责人：** 技术负责人批准并执行生产部署。

按[发布清单](#218-发布清单)执行，三端的差异见[第 13 章](#13-发布与回滚)。

**闸门：** 健康检查和核心流程验证通过，观察期内没有明显异常。

### 5.10 运营维护

上线后持续关注错误日志、服务可用性、模型调用的失败率和成本、用户反馈、证书和依赖的到期及安全更新、备份状态。详见[第 18 章](#18-上线后的运营)。

### 5.11 结项与复盘

**客户项目结项：**

- [ ] 取得验收确认
- [ ] 交付物齐全，见 [16.3](#163-交付物)
- [ ] 密钥已转交或轮换
- [ ] 已检查 `.trellis`、日志和 AI 会话记录中有没有不应交付的内容
- [ ] 依赖和工具的许可证已检查
- [ ] 质保期和后续支持方式明确

**复盘至少回答：**

1. 哪些估算偏差最大，为什么？
2. 哪些问题到开发后期才发现，能否提前发现？
3. AI 反复犯了什么错？是否已写入规范、Skill 或自动检查？
4. 哪些代码或配置值得提炼回模板？

## 6. 需求与规格

### 6.1 用什么记录需求

| 需求 | 文档 | 位置 |
|---|---|---|
| 小改动、缺陷 | Issue，写清验收标准 | GitHub Issues |
| 普通功能 | 一页 PRD | `docs/prd/` |
| 业务规则复杂、长期迭代、容易有争议 | OpenSpec 变更 | `openspec/changes/` |
| 架构和技术决定 | ADR | `docs/adr/` |
| 不确定是否可行 | 技术探索结论 | Issue 评论或 `docs/adr/` |

**同一份需求只有一个权威来源。** 用了 OpenSpec 时，Issue、PRD 和 Trellis 任务里只放链接，不重复写需求。

### 6.2 把需求写到可以验证

| 不好的写法 | 好的写法 |
|---|---|
| 系统要快 | 列表页在 1000 条数据下 2 秒内加载完成 |
| 支持文件上传 | 支持 PDF 和 DOCX，单个不超过 20 MB；超限时提示原因，不创建任务 |
| AI 回答要准确 | 固定评估集中，关键问题都给出来源；资料中没有答案时明确说明 |
| 要有权限控制 | 普通成员只能查看本组织的文档，管理员才能删除，跨组织访问返回 404 |

### 6.3 OpenSpec 的使用方法

OpenSpec 用来管理复杂业务的行为规格。`openspec` 开头的命令在终端运行，`/opsx:` 开头的命令在 AI 对话框中运行。

**项目初始化（每个项目一次，由技术负责人执行）：**

```bash
npm install -g @fission-ai/openspec@latest   # 需要 Node.js 22.12.0 及以上（1.16.0 的要求）
cd my-project
openspec init --tools claude,cursor
```

`--tools` 填团队实际使用的工具。其他工具的取值以 `openspec init` 的交互提示和 `openspec init --help` 为准；不加参数运行 `openspec init`，也可以交互选择。然后编辑 `openspec/config.yaml`：

```yaml
schema: spec-driven
context: |
  这里写项目用途、主要用户、技术栈和第一期范围。
  完成前必须运行 make check。
rules:
  proposal:
    - 必须写明本次不做什么
    - 业务不明确的地方列入“待确认问题”，不得自行假设
  specs:
    - 每条需求都包含正常、错误和权限场景
  tasks:
    - 每个任务不超过半天，并写明验证方式
```

把 `openspec/` 和生成的工具配置提交到仓库，其他成员拉取后就能使用。

**开发一个功能的流程：**

| 步骤 | 操作 | 谁来做 |
|---|---|---|
| 1. 建分支 | `git switch -c feat/123-disqualification-extraction` | 开发者 |
| 2. 梳理问题 | `/opsx:explore`，让 AI 只列出业务上不明确的问题，不写代码 | 开发者 |
| 3. 业务确认 | 拿问题找业务拍板人确认 | 项目负责人 |
| 4. 生成提案 | `/opsx:propose add-disqualification-extraction` | 开发者 |
| 5. 校验 | `openspec validate add-disqualification-extraction --strict` | 开发者 |
| 6. 评审 | 提一个只包含规格的 PR，业务拍板人看场景，技术负责人看方案 | 业务拍板人、技术负责人 |
| 7. 实现 | `/opsx:apply add-disqualification-extraction`，照常提交、过 CI 和审查 | 开发者 |
| 8. 归档 | 验收通过后 `/opsx:archive add-disqualification-extraction` | 开发者 |
| 9. 检查 | `git diff openspec/specs`，确认主规格确实更新 | 审查者 |

`/opsx:propose` 会在 `openspec/changes/<变更名>/` 下生成：

| 文件 | 内容 | 审查重点 |
|---|---|---|
| `proposal.md` | 为什么做、范围和方案 | 范围是否正确，有没有多做 |
| `specs/` | 新增、修改或删除的需求和场景 | 正常、错误和权限场景是否齐全 |
| `design.md` | 技术方案 | 是否符合现有架构 |
| `tasks.md` | 实现清单 | 顺序是否合理，有没有遗漏 |

需求写法示例：

```markdown
## ADDED Requirements
### Requirement: 提取废标条款
系统必须从招标文件中提取废标条款，并标明原文位置。

#### Scenario: 找到明确的废标条款
- GIVEN 招标文件中包含明确的废标条款
- WHEN 系统完成解析
- THEN 列出该条款和原文页码，状态为“待人工确认”

#### Scenario: 无法判断是否属于废标条款
- GIVEN 某条款含义不明确
- WHEN 系统完成解析
- THEN 标记为“需要人工判断”，不得自动忽略
```

**常用终端命令：**

```bash
openspec list                     # 进行中的变更
openspec show <变更名>            # 查看变更
openspec view                     # 总览
openspec validate --all --strict  # 放进 CI 做格式检查
```

不同 Agent 中的命令写法可能不同，比如 `/opsx:propose` 或 `/opsx-propose`，以 `openspec init` 的输出为准。

### 6.4 OpenSpec 的团队规则

1. **待确认问题没解决，不运行 `apply`。**
2. **需求变了，先改规格，再改代码。**
3. **规格由业务拍板人确认，** 不由 AI 或开发者单方面决定。
4. **老项目不补写全部规格，** 只为接下来要改的功能写，否则会把现有缺陷写成“正确需求”。
5. **同时有多个变更时，命令都带上变更名。**
6. **归档后检查主规格。** 有用户反映过归档后主规格没更新也没报错的问题，所以每次都用 `git diff openspec/specs` 确认。
7. **规格不能代替测试和评估。** AI 功能还要用真实样本和评估集验收。
8. **业务不确定时先做小试验。** 结果确认后再写成正式规格，试验代码默认不合并。

### 6.5 OpenSpec 与 Trellis 的分工

| 内容 | 放在哪里 |
|---|---|
| 系统应该怎样（业务规则、场景） | OpenSpec |
| 团队怎么开发（编码规范、流程） | `.trellis/spec`、`AGENTS.md` |
| 当前任务的上下文和进度 | `.trellis/tasks`，其中链接 OpenSpec 变更 |
| 任务分配和状态 | GitHub Issues + Projects |

## 7. 任务管理与协作节奏

### 7.1 看板

用 GitHub Projects 管理，每个项目一个看板。

| 列 | 含义 | 进入条件 |
|---|---|---|
| Backlog | 待整理 | 有人提出，尚未确认 |
| Ready | 可以开工 | 满足可开工标准 |
| In Progress | 开发中 | 有负责人，已建分支 |
| In Review | 审查中 | PR 已提交，CI 通过，已指定审查人 |
| Testing | 验证中 | 已合并，已部署到测试环境 |
| Done | 已完成 | 满足完成标准 |
| Blocked | 被阻塞 | 写明卡在哪里、等谁、预计何时解决 |

**字段：** 负责人（一人）、优先级（P0 至 P3）、规模（S、M、L）、风险（L1 至 L3）、模块（web、miniapp、desktop、api、infra）、里程碑。

**标签：** `type:feature`、`type:bug`、`type:chore`、`type:spike`、`risk:l3`、`needs:decision`、`client-visible`。

### 7.2 可开工标准

任务进入 Ready 前要同时满足：

- [ ] 目标一句话说得清
- [ ] 验收标准可以验证
- [ ] 范围和非范围明确
- [ ] 依赖的接口、设计或资料已就绪，或写明了假设
- [ ] 已标注规模和风险
- [ ] 已链接相关的 PRD、OpenSpec 变更和代码位置
- [ ] 不超过 2 个工作日，否则继续拆分

### 7.3 完成标准

任务进入 Done 前要同时满足：

- [ ] 验收标准全部满足
- [ ] 测试已补充且通过
- [ ] CI 全部通过
- [ ] 人工审查通过
- [ ] 文档、API 类型、规格和规范已同步
- [ ] 已在目标环境验证
- [ ] 高风险改动有回滚方案
- [ ] 过程中发现的遗留问题已建 Issue

### 7.4 任务拆分原则

- **按可以验证的结果拆。** 比如“用户可以上传文档”，而不是“写 Service 层”。
- **一个任务一个 PR。** 太大就拆成多个可以单独合并的任务。
- **先走通，再加强。** 先打通最小流程，再加错误处理和性能优化。
- **减少共享文件。** 容易冲突的公共改动单独做成一个任务，先合并。

### 7.5 进行中的数量限制

- 每人同时最多 1 个主任务在 In Progress，另外最多 1 到 2 个 PR 在等审查。
- 每人同时运行的并行 Agent 任务不超过 2 到 3 个。
- 团队待审 PR 超过“人数 × 2”时，先清审查队列，不开新任务。

Agent 可以同时写很多代码，但人的审查和判断能力有限。积压的 PR 越多，审查质量越差，冲突也越多。

### 7.6 优先级

| 优先级 | 含义 | 处理方式 |
|---|---|---|
| P0 | 线上核心功能不可用，或有数据、安全问题 | 立即处理，可以中断其他工作 |
| P1 | 影响当前里程碑或重要客户 | 本迭代优先 |
| P2 | 常规计划内的工作 | 按排期 |
| P3 | 有价值但不紧急 | 留在 Backlog，定期清理 |

### 7.7 固定节奏

| 活动 | 频率 | 时长 | 参与者 | 产出 |
|---|---|---|---|---|
| 每日同步 | 每天 | 异步，或不超过 15 分钟 | 项目成员 | 今日任务、阻塞项 |
| 迭代计划 | 每周 | 30 到 60 分钟 | 项目成员 | 迭代目标和任务 |
| 方案评审 | 按需 | 30 到 60 分钟 | 相关人员 | 决定和 ADR |
| 演示 | 每个迭代结束 | 30 分钟 | 项目成员、业务拍板人 | 反馈和验收问题 |
| 团队复盘 | 每两周 | 30 到 45 分钟 | 项目成员 | 最多 3 个改进项 |
| AI 与规范回顾 | 每两周 | 30 分钟 | 开发者、模板负责人 | 规范、Skill 和模板的更新 |

能在 Issue 或 PR 中讲清楚的事，就不开会。

**每日异步同步**（团队群或固定的 Issue，三行就够）：

```text
昨天：完成 #203 检索接口，PR 已提交
今天：处理 #203 的审查意见，开始 #205 的评估用例
阻塞：等客户提供测试文档（@项目负责人）
```

发现阻塞时立刻说，不等到第二天。

**迭代：** 默认一周一个迭代，需求稳定、任务较大时可以改为两周。迭代结束时演示能运行的结果；没完成的任务回到 Backlog 重新评估，不自动顺延。

**AI 与规范回顾**要回答：

- 这段时间 AI 反复犯了什么错？
- 审查中反复出现哪些意见？
- 哪条规范不清楚、过时了，或一直没人遵守？
- 哪些规则可以改成 lint、测试或 CI 检查？
- 有哪些好用的提示词或做法可以共享？
- AI 工具的成本是否合理？

输出最多 3 项改动，通过 PR 更新规范或 Skill。

## 8. 人与 AI 协作

### 8.1 分工边界

| 适合交给 AI | 人和 AI 一起做 | 必须由人决定 |
|---|---|---|
| 样板代码和增删改查 | 技术方案和接口设计 | 产品目标和优先级 |
| 按明确规格实现功能 | 复杂缺陷排查 | 架构和不可撤销的决定 |
| 测试初稿 | 重构方案 | 是否上线、是否回滚 |
| 文档初稿和代码解释 | 安全审查 | 权限、计费和数据处理规则 |
| 第一轮代码审查 | 性能分析 | 是否合并、是否验收 |

### 8.2 工具体系

成员可以使用不同的 AI 编码工具，团队统一的是**规范、命令和门禁**。

| 层级 | 工具 | 说明 |
|---|---|---|
| 主规则 | `AGENTS.md`（`CLAUDE.md` 只写 `@AGENTS.md`） | 所有 Agent 都读取 |
| 规范和任务上下文 | Trellis（`.trellis/`） | 为每种 Agent 生成入口，共用同一份规范 |
| 公司 Skill | `.agents/skills/team-*` | 调试、完成前验证、处理审查意见等 |
| 复杂需求 | OpenSpec | 见 [6.3](#63-openspec-的使用方法) |
| 统一命令 | `Makefile` | `make check` 等 |
| 门禁 | Git hook、CI、人工审查 | 与工具无关 |

配置方法见《公司项目脚手架规范》第 6 章。暂不使用的工具：Superpowers 整套流程（只挑选其中的 Skill 改写成公司 Skill）、Multica 等 Agent 调度平台（多人同时跑很多 Agent 且开始混乱时再评估）。

### 8.3 AI 工具准入

技术负责人维护一张公司认可的工具表：

| 工具 | 账号归属 | 用途 | 可接触的数据 | 月预算 | 负责人 |
|---|---|---|---|---|---|
| 示例：Claude Code | 公司 | 开发 | 内部代码、已授权的客户代码 | 按人设定 | 技术负责人 |

每种工具至少确认：

- 用公司账号还是个人账号？费用谁承担？
- 数据是否用于训练？保存多久？服务在哪个地区？
- 能否处理客户代码和客户数据？
- 能否限制可访问的文件、可执行的命令和网络？
- 能否查看用量和费用？
- 成员离职时能否立即收回权限？

**正式支持范围：** 模板负责人维护 2 到 3 种主力 Agent 的适配。其他 Agent 也可以用，但适配由使用者自己负责，同样要通过 CI 和审查。

**新 Agent 验证清单：**

- [ ] 能自动读取 `AGENTS.md` 或 Trellis 生成的入口
- [ ] 能发现并触发一个公司 Skill
- [ ] 能运行 `make check`，并如实报告结果
- [ ] 能遵守文件和命令权限
- [ ] 违反规则时，会被 Git hook 或 CI 拦住
- [ ] 数据政策符合公司要求

### 8.4 使用 Trellis 的日常流程

**加入项目：**

```bash
npm install -g @mindfoldhq/trellis@latest
cd my-project
make setup
trellis init -u <你的名字>
```

按生成的上手任务阅读项目规范。只需为自己使用的工具生成入口时，在命令后加上对应参数，比如 `--cursor`。

**处理一个任务：**

```text
1. 创建分支或 worktree
2. 把 Issue 的目标、验收标准和相关链接交给 AI
3. AI 按 Plan → Execute → Finish 工作
4. AI 卡住或跳步时，运行 /trellis:continue
5. 人工测试并提交，走 PR 流程
6. 运行 /trellis:finish-work，归档任务；如果它改动了应提交的文件，提交到同一个 PR
```

不同工具中的命令写法可能不同，以 Trellis 当前文档为准。Trellis 的流程不能替代 PR、CI 和人工审查。

### 8.5 一次 AI 开发循环

```text
准备上下文 → 让 AI 复述和计划 → 人确认 → 小步实现 → 运行检查
     ▲                                                │
     └──────── 结果不对：修正规格或规范，再继续 ◀───────┘
```

1. **准备上下文：** 目标、验收标准、非范围、相关规范和相近的代码。
2. **先要计划：** AI 说明理解、要改的文件、方案、风险和验证方法，确认前不大范围改文件。
3. **小步实现：** 每完成一步就运行相关检查并提交。
4. **要求证据：** 让 AI 实际运行测试，查看命令输出，不接受“应该可以”。
5. **人工检查：** 亲自走主要流程，看完整 diff。
6. **沉淀：** 把发现的通用问题写回规范或 Skill。

### 8.6 任务指令模板

```markdown
## 任务
Issue #123：<标题>

## 目标
<一句话说明要解决什么问题>

## 验收标准
- [ ] ...
- [ ] ...

## 非范围
- 不修改 ...
- 不引入新依赖，确有需要先说明理由

## 必读内容
- 需求：docs/prd/... 或 openspec/changes/...
- 规范：.trellis/spec/...
- 参考实现：services/api/app/modules/example_items/

## 约束
- 只修改与当前任务相关的文件
- 数据库结构变更必须通过迁移
- 新增或改变行为时补充测试
- 不删除或放宽已有测试来通过检查

## 工作方式
1. 先阅读相关代码，再输出计划，等我确认后再实现
2. 不确定的地方先提问，不要自行假设
3. 完成后运行 make check，贴出真实结果
4. 最后说明：改了什么、怎么验证、还有什么风险
```

### 8.7 会话管理

- **一个任务一个会话。** 新任务开新会话，减少无关上下文。
- **会话太长或走偏时，不要硬撑。** 先让 AI 把当前状态和下一步写进任务文件，再开新会话。
- **连续两次修不好，就停下来。** 由人重新分析根因，或者把问题描述清楚后重开会话。
- **不依赖聊天记录。** 重要结论都写进 Issue、PRD、OpenSpec、ADR 或规范。

### 8.8 AI 结果的检查重点

| 常见问题 | 检查方法 |
|---|---|
| 虚构不存在的 API 或依赖 | 实际运行，核对官方文档和依赖来源 |
| 改动超出范围 | 看 diff 中每个文件为什么被改 |
| 重复实现已有功能 | 搜索现有代码，对照公共模块 |
| 测试只是在迎合实现 | 看断言是否验证业务行为；故意改错，看测试会不会失败 |
| 修改或删除测试来通过 CI | 审查测试文件的变化 |
| 吞掉异常 | 查看错误处理和日志 |
| 遗漏权限检查 | 为未授权和跨租户场景写测试 |
| 只考虑正常流程 | 按验收标准验证错误场景和边界情况 |
| 声称完成，但没有运行 | 查看 CI 和命令输出 |

### 8.9 数据和权限纪律

- 不把密钥、生产数据或未经授权的客户资料发给 AI 工具。数据分级见 [17.1](#171-数据分级)。
- 客户项目只使用合同或客户确认允许的 AI 工具。
- AI 编码工具只开放任务需要的目录和权限。
- 不让 AI 直接操作生产数据库或生产服务器。
- AI 读取的网页、Issue、依赖代码和第三方 Skill 中可能藏有恶意指令，不要盲目执行。
- 新依赖要确认真实存在、仍在维护，并检查许可证和已知漏洞。

### 8.10 AI Agent 的 Git 权限

写进 `AGENTS.md`，并尽量通过各工具的权限设置落实：

| 权限 | 操作 |
|---|---|
| 可以直接执行 | `git status`、`git diff`、`git log`、在任务分支上提交、`gh pr view`、`gh pr checks` |
| 需要人确认 | `git push`、`gh pr create`、`git rebase`、删除文件、修改 CI 和依赖 |
| 不允许 | 推送或强推 `main` 和 `release/*`、`git reset --hard`、`git clean -fd`、打发布标签、合并或批准 PR、修改仓库设置和密钥 |

使用自动化 Agent 或机器人账号时：使用权限最小的令牌，只开放需要的仓库；机器人创建的 PR 要指定一名负责人，这个人必须看完并能解释改动；机器人的 PR 同样需要人工批准。

### 8.11 把错误变成规范

AI 每次犯错时，按下面的顺序选择最稳妥的防线：

```text
能用类型系统或 lint 拦截？ → 加规则
能用测试或 CI 拦截？       → 加测试或检查
能写成明确的规范？         → 写入 .trellis/spec，附正确示例的路径
是一类做事方法？           → 写成或改进公司 Skill
都不适合？                 → 写进审查清单
```

不要把 `AGENTS.md` 写成一份越来越长的错误清单，它只放关键入口和必须遵守的规则。

### 8.12 AI 成本管理

- 按项目和成员统计 AI 工具的费用。
- 简单任务不用最贵的模型，具体选择按实际效果定。
- 避免 Agent 长时间无人看管地运行；自动化任务设置时间和费用上限。
- 把成本和产出放在一起看，不单独追求降低成本。

## 9. 多人并行开发

### 9.1 总原则

多人协作的冲突主要来自两个原因：**接口没有先定好**，以及**多人同时改同一批文件**。AI 的改动范围通常更大，会放大这两个问题。所以要做到：

1. 模块有负责人。
2. 接口先行。
3. 分支短，PR 小。
4. 公共文件有协调规则。
5. 上下文写进仓库。

### 9.2 模块负责制

项目开始时，在 `README.md` 中写明模块负责人：

| 模块 | 负责人 | 备份 | 风险 |
|---|---|---|---|
| `services/api/.../auth` | 张三 | 李四 | L3 |
| `services/api/.../ai_gateway` | 李四 | 张三 | L3 |
| `apps/web/src/features/ai-chat` | 王五 | 李四 | L2 |
| `.github/workflows`、`scripts/` | 技术负责人 | 模板负责人 | L3 |

负责人不是唯一能改代码的人，而是负责把关设计，改动这个模块的 PR 要请他审查。免费计划的私有仓库中 CODEOWNERS 不会自动生效，所以由作者在 PR 中手动指定审查人。

### 9.3 接口先行

前后端或多人共同开发一个功能时：

```text
1. 指定一人写接口契约：路径、请求、响应和错误码
2. 负责人审查契约
3. 先合并后端的请求和响应定义及占位接口，生成 OpenAPI 和 TS 类型
4. 后端实现真实逻辑
5. 前端基于生成的类型和模拟数据开发
6. 联调；契约有变化时，单独提 PR
```

**规则：**

- 前端不手写重复的接口类型，统一使用 `packages/api-types`。
- 契约有变化时，同时通知后端和各客户端的负责人。
- 已发布的接口不随意破坏。小程序和桌面端的旧版本可能长期存在，优先新增字段，确实需要不兼容的改动时走新版本接口。

### 9.4 容易冲突的公共文件

| 文件 | 规则 |
|---|---|
| Alembic 迁移 | 合并前同步 `main`；出现多个 head 时，由后合并的人解决，见 [10.13](#1013-同步分支和处理冲突) |
| Prisma 迁移 | 不修改已发布的迁移；同步后有冲突时，删除自己未合并的迁移，重新生成 |
| Drizzle 迁移（桌面） | 同 Prisma |
| 依赖锁文件 | 不手工合并，取 `main` 的版本后重新生成 |
| 生成的 OpenAPI 和 TS 类型 | 不手工合并，重新生成，CI 比对 |
| 路由和模块注册文件 | 改动尽量小 |
| 设计变量和全局样式 | 负责人审查，大的改动提前通知 |
| `AGENTS.md`、`.trellis/spec`、公司 Skill、CI | 单独提 PR，由模板负责人或技术负责人审查 |

### 9.5 使用 worktree 并行

一个人同时运行多个 AI 任务时，每个任务使用独立的 worktree：

```bash
git fetch origin
git worktree add ../my-project-203 -b feat/203-doc-search origin/main
cd ../my-project-203
make setup
```

清理：

```bash
git worktree remove ../my-project-203
git branch -D feat/203-doc-search   # 先确认 PR 已合并
```

PR 用 Squash Merge 合并后，`git branch -d` 会提示分支没有完全合并，所以确认已合并后用 `-D` 删除。

**注意：**

- 每个 worktree 使用独立的端口、环境变量和测试数据库。
- 并行的任务之间尽量没有依赖，也不改同一批文件。
- 有依赖的任务串行进行，或先合并基础任务。
- 不要在同一个目录中同时运行两个会改文件的 Agent。

### 9.6 多人共同开发一个功能

优先把功能拆成多个任务。必须共享时：

| 方式 | 做法 | 注意 |
|---|---|---|
| 功能开关（推荐） | 未完成的功能可以合并到 `main`，但默认关闭 | 开关有负责人；全量上线后及时删除开关和旧代码；不用开关隐藏未审查的 L3 改动 |
| 堆叠 PR | 第二个 PR 基于第一个的分支 | 不超过 2 层 |
| 临时共享分支 | 多人在同一分支上提交 | 只用 merge 同步，不改写历史；提前定好负责人和最晚合并时间 |

### 9.7 任务交接

人员或会话切换时，交接信息写在 Issue、PR 或 `.trellis/tasks` 中，不写在私聊里，使用[交接模板](#217-任务交接)。接手的人要能回答：

1. 目标和验收标准是什么？
2. 现在做到哪一步了？
3. 哪些决定已经定了，为什么？
4. 试过哪些方法没有成功？
5. 下一步是什么，怎么验证？

### 9.8 工作时间不重叠时

- 所有决定写进 Issue 或 PR，不依赖口头同步。
- 下班前更新看板，并推送可以恢复的工作分支（不合并）。
- PR 描述写到审查人不用问你就能审。
- 涉及 L3 改动或客户沟通时，提前约好共同在线的时间。

## 10. Git 与 GitHub 操作

本章前半部分（10.1 至 10.6）是规则，后半部分（10.7 至 10.21）是从建仓库到结项的具体操作。文中的 `TIanle-art` 是当前的 GitHub 账号，转到组织后换成组织名；`client-acme-portal` 和编号都是示例，请换成实际值。

### 10.1 免费计划下的权限约定

个人账号的私有仓库中，所有协作者的权限都相同，GitHub 不会阻止他们推送 `main` 或合并 PR。下面这些规则要靠约定执行，由 Git hook 和 `main` 守卫辅助发现问题：

| 操作 | 谁可以做 | 辅助手段 |
|---|---|---|
| 推送功能分支、创建 PR | 所有成员 | |
| 批准 PR | 作者以外的成员；L3 必须由技术负责人批准 | GitHub 不允许作者批准自己的 PR |
| 合并 PR | 作者，在 CI 通过并获得批准后；L3 由技术负责人合并 | `main` 守卫检查 PR 和批准 |
| 直接推送 `main`、更新 `release/*` | 任何人都不可以 | pre-push hook 阻止，`main` 守卫发现 |
| 打发布标签、创建 Release | 技术负责人 | 约定 |
| 部署生产环境 | 技术负责人及其备份 | 只有他们有服务器权限 |
| 修改仓库设置、邀请协作者 | 仓库所有者 | GitHub 限制 |
| 修改 CI、部署脚本 | 所有成员都能改，但属于 L3 | 技术负责人审查 |

`main` 守卫报错时，技术负责人当天核查：确认改动内容，必要时补一个审查 PR 或回退，并在团队频道说明原因。

### 10.2 分支模型

使用基于 `main` 的短分支开发，不设长期的 `develop` 分支。

```text
main                         # 始终可以部署
├── feat/123-user-login      # 功能
├── fix/456-token-refresh    # 缺陷修复
├── chore/789-upgrade-deps   # 工程事务
├── docs/321-release-guide   # 文档
├── spike/654-rag-parser     # 技术探索，默认不合并
├── hotfix/987-pay-callback  # 线上紧急修复
├── revert/456-doc-upload    # 撤销已合并的改动
└── release/1.2.x            # 需要修复旧版本时才创建
```

命名规则：`<类型>/<Issue 编号>-<简短英文描述>`。

### 10.3 提交信息

```text
<类型>(<范围>): <说明>
```

类型：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`ci`、`revert`。

```text
feat(auth): 支持短信验证码登录
fix(api): 修复刷新令牌的过期判断
docs(handbook): 更新发布流程
```

- 一次提交只做一件事。
- 说明写清楚为什么改，不只写“修改代码”。
- PR 标题使用同样的格式，因为 Squash Merge 后它会成为 `main` 上的提交信息。

### 10.4 PR 大小

| 有效改动 | 处理方式 |
|---|---|
| 不超过 200 行 | 理想大小 |
| 200 到 400 行 | 可以接受 |
| 超过 400 行 | 尽量拆分；无法拆分时说明理由，并给出审查顺序 |

生成代码、锁文件和纯格式化不计入，但纯格式化要单独提 PR。AI 一次改了很多文件时，先按功能或层次拆成多个 PR，再提交审查。

### 10.5 PR 的生命周期

```text
Draft → CI 通过 → Ready for review → 指定审查人 → 审查和修改
→ 批准 → Squash Merge → 删除分支 → 确认部署
```

- 想尽早获得方向上的反馈时，开 Draft PR。
- 先完成自检，再请求审查。审查人不应该是第一个读这段代码的人。
- 审查意见逐条回应；有争议的讨论由提出人或负责人关闭。
- 新提交推送后，如果改动较大，重新请求审查。免费计划不会自动让旧的批准失效，审查人要留意。
- 统一使用 Squash Merge，让 `main` 上一个 PR 对应一个提交，便于回滚和查找。

### 10.6 不该提交的内容

- 密钥、令牌、真实的 `.env`
- 真实客户数据和数据库备份
- 个人 IDE 配置和本地日志
- AI 会话的原始记录，除非确认没有敏感信息且团队确实需要
- 没有确认过的大型二进制文件

**密钥一旦提交，先轮换密钥，再清理历史。** 只删除文件是不够的。

### 10.7 全流程操作总览

| 阶段 | 操作人 | 操作 | 详见 |
|---|---|---|---|
| 个人准备 | 每位成员 | 安装和配置 Git、`gh`，登录账号 | [10.8](#108-配置个人环境) |
| 立项 | 技术负责人 | 用模板建仓库，设置合并方式、协作者、标签和看板 | [10.9](#109-创建新项目) |
| 需求和拆任务 | 项目负责人、开发者 | 创建 Issue 和里程碑，用 PR 提交 PRD 或规格 | [10.10](#1010-管理需求和任务) |
| 开发 | 开发者 | 建分支、提交、推送、开 PR、看 CI、合并 | [10.11](#1011-开发者日常操作) |
| 审查 | 审查者 | 查看待审 PR，拉到本地验证，批准或要求修改 | [10.12](#1012-审查者操作) |

### 10.8 配置个人环境

每位成员做一次。安装 Git、[GitHub CLI](https://cli.github.com/)（命令是 `gh`）和 gitleaks，然后运行：

```bash
git config --global user.name "张三"
git config --global user.email "zhangsan@your-company.com"
git config --global init.defaultBranch main
git config --global pull.rebase true
git config --global fetch.prune true
git config --global push.autoSetupRemote true

gh auth login
gh auth refresh -s project   # 需要用命令操作 Projects 时
gh auth status
```

- `pull.rebase true`：`git pull` 时不产生多余的合并提交。
- `fetch.prune true`：自动清理远程已删除的分支记录。
- `push.autoSetupRemote true`：新分支第一次推送时不用加 `-u`，需要 Git 2.37 或更高版本。
- `user.email` 要用已添加到 GitHub 账号的邮箱，提交才会关联到本人。
- 每次克隆项目后都运行一次 `make setup`，它会启用项目的 Git hook。

### 10.9 创建新项目

由技术负责人或仓库所有者操作。

**第 1 步：用模板创建仓库**

```bash
gh repo create TIanle-art/client-acme-portal \
  --template TIanle-art/template-web \
  --private \
  --clone
cd client-acme-portal
make setup
```

**第 2 步：设置合并方式**

```bash
gh repo edit TIanle-art/client-acme-portal \
  --enable-squash-merge \
  --squash-merge-commit-message pr-title \
  --enable-merge-commit=false \
  --enable-rebase-merge=false \
  --delete-branch-on-merge
```

这样只允许 Squash Merge，合并后的提交信息使用 PR 标题，并自动删除已合并的分支。

**第 3 步：邀请协作者**

```bash
gh api -X PUT repos/TIanle-art/client-acme-portal/collaborators/<GitHub 用户名>
```

被邀请的人要在邮件或 GitHub 通知中接受邀请。个人仓库的协作者都有写权限，只邀请需要参与开发的人；外包和客户人员只在必要时邀请，项目结束后移除。

**第 4 步：完成项目初始化**

```bash
git switch -c chore/1-project-setup
trellis init -u <你的名字> --claude --cursor --codex --copilot --opencode --kimi \
  --registry gh:TIanle-art/spec-templates/marketplace --template team-base
# 按技术栈追加规范，例如 FastAPI 和网页项目：
trellis init --registry gh:TIanle-art/spec-templates/marketplace --template team-fastapi --append
trellis init --registry gh:TIanle-art/spec-templates/marketplace --template team-web --append
# 从 handbook 仓库的 project-kit 复制公共基线文件，见其 README
# 补全 README.md、AGENTS.md 和 .env.example，写明模块负责人
git status    # 确认列出的文件都应该提交，没有密钥和临时文件
git add -A
git commit -m "chore: 初始化项目配置"
git push
gh pr create --title "chore: 初始化项目配置" --body "初始化项目规范、Trellis 和 CI。"
```

Trellis 的参数只保留团队实际使用的工具，以当前官方文档为准。

**第 5 步：确认 CI 和 `main` 守卫**

初始化 PR 合并后，在 Actions 页面确认 CI 和 `main-guard` 都运行成功。

**第 6 步：创建标签和看板**

```bash
for label in type:feature type:bug type:chore type:spike risk:l3 needs:decision client-visible; do
  gh label create "$label" --repo TIanle-art/client-acme-portal --force
done

gh project create --owner @me --title "client-acme-portal"
```

看板的列和字段按 [7.1](#71-看板) 设置。可以开启 Project 的内置自动规则，比如新 Issue 自动加入看板、PR 合并后自动移动状态。

```bash
gh issue view 123
gh issue edit 123 --add-assignee @me
```

**加入看板：**

### 10.11 开发者日常操作

以 Issue #123 为例。

**第 1 步：从最新的 `main` 建分支**

```bash
git switch main
git pull
git switch -c feat/123-doc-upload
```

也可以用 `gh` 建分支，它会自动关联 Issue：

```bash
gh issue develop 123 --name feat/123-doc-upload --base main --checkout
```

并行多个任务时使用 worktree，见 [9.5](#95-使用-worktree-并行)。

**第 2 步：让 AI 实现，小步提交**

```bash
git status
git diff
git add services/api/app/modules/docs/ services/api/tests/test_docs.py
git commit -m "feat(docs): 支持上传 PDF 文档"
```

- 每次提交前都看一遍改动。
- 尽量按路径添加文件，不要习惯性地 `git add .`。AI 可能生成了临时文件、日志或无关改动。
- 分支上的提交可以细一些，合并时会压缩成一个。
- pre-commit hook 会检查当前分支和密钥。被拦住时先看原因，不要直接加 `--no-verify`。

**第 3 步：尽早推送，开 Draft PR**

```bash
git push
gh pr create --draft \
  --base main \
  --title "feat(docs): 支持上传 PDF 文档" \
  --body-file ../pr-123.md
```

PR 内容按 [21.6](#216-pr-模板) 填写，可以让 AI 起草，但提交前要人工核对。正文写上 `Closes #123`，合并到 `main` 后 Issue 会自动关闭。

**第 4 步：自检，转为待审查**

```bash
make check
gh pr checks --watch
gh pr diff
gh pr ready
gh pr edit --add-reviewer <审查人>   # 模块负责人；L3 改动请技术负责人
```

使用 Trellis 时，运行 `/trellis:finish-work` 后再执行一次 `git status`。如果它改动了应提交的文件，提交到同一个 PR。

**第 5 步：处理审查意见**

```bash
gh pr view --comments
# 修改后
git add <改动的文件>
git commit -m "fix(docs): 校验上传文件的大小"
git push
gh pr edit --add-reviewer <审查人>   # 改动较大时，请求重新审查
```

- 用新的提交修改，不改写已审查的提交，这样审查人只看新增部分。
- 同意的意见修改后回复；不同意的说明理由。

**第 6 步：合并**

确认三件事后再合并：CI 全部通过、至少一人批准、批准之后没有未审查的大改动。

```bash
gh pr view
gh pr merge --squash --delete-branch
```

合并前检查 PR 标题，它会成为 `main` 上的提交信息。

**第 7 步：确认结果，同步本地**

```bash
git switch main
git pull
gh run list --branch main --limit 5
```

确认 CI、`main-guard` 和测试环境部署都成功后，把任务移到 Testing。

**阅读改动：**


### 10.13 同步分支和处理冲突

**什么时候同步：** 请求审查前、分支存在超过 2 到 3 天时，以及 GitHub 提示有冲突时。

**自己的分支用 rebase：**

```bash
git fetch origin
git rebase origin/main
make check
git push --force-with-lease
```

`--force-with-lease` 会先检查远程分支是否被别人更新过，比 `--force` 安全。不要在 `main`、`release/*` 和多人共用的分支上使用。

**多人共用的分支用 merge：**

```bash
git fetch origin
git merge origin/main
git push
```

**遇到代码冲突：**

```bash
git status                  # 查看冲突的文件
# 打开文件，理解两边的改动，解决冲突标记
git add <已解决的文件>
git rebase --continue
```

处理乱了，可以放弃这次 rebase，回到开始前的状态：

```bash
git rebase --abort
```

AI 帮忙解决冲突后，人必须检查结果，不能只看 CI 是否通过。

**注意 ours 和 theirs 的含义：**

| 操作 | `--ours` | `--theirs` |
|---|---|---|
| `git rebase origin/main` | `main` 的版本 | 你正在重放的提交 |
| `git merge origin/main` | 你当前分支的版本 | `main` 的版本 |

rebase 时这两个词的含义和直觉相反，很容易选错。

**依赖锁文件冲突：** 不手工合并，取 `main` 的版本后重新生成。

```bash
# Python（rebase 过程中）
git checkout --ours -- services/api/uv.lock
(cd services/api && uv lock)
git add services/api/uv.lock
git rebase --continue
```

```bash
# Node（rebase 过程中）
git checkout --ours -- pnpm-lock.yaml
pnpm install --lockfile-only
git add pnpm-lock.yaml
git rebase --continue
```

**生成的文件冲突：** OpenAPI 和 TS 类型同样不手工合并，同步源代码后重新生成。

**Alembic 出现多个 head：**

```bash
cd services/api
uv run alembic heads
```

把**自己未合并的迁移**的 `down_revision` 改成 `main` 上最新的 revision，让迁移保持一条线，然后在测试数据库上重新运行。已发布的迁移不修改。

**Prisma 迁移冲突：** 删除自己未合并的迁移目录，同步 `main` 后重新运行 `pnpm prisma migrate dev`。

**让 GitHub 更新 PR 分支：** 没有冲突时，也可以运行：

```bash
gh pr update-branch 456 --rebase
```

之后在本地先运行 `git pull --rebase`，再继续开发。

### 10.14 发布版本

**版本号：**

- 只有一个发布物的项目，标签用 `v1.3.0`。
- 同一仓库中多个端各自发布时，用 `api-v1.3.0`、`desktop-v1.3.0`、`miniapp-v1.3.0`。
- 桌面和小程序的版本号写在代码中，先用 PR 更新版本号，合并后再打标签。

**测试环境：** `main` 合并后自动部署。

**生产发布（技术负责人）：**

```bash

git pull
git log --oneline v1.2.0..HEAD        # 查看本次发布的内容
```

打标签前先完成[发布清单](#218-发布清单)中的发布前检查。部署脚本见《公司项目脚手架规范》13.5 节。

**各端的额外操作：**

| 端 | 打标签后 |
|---|---|
| 后端、网页 | CI 构建，维护者部署，健康检查，观察 |
| 小程序 | 上传代码，体验版验证后提交审核；在 Release 中记录审核和发布状态 |
| 桌面 | CI 构建三个平台的测试版本；维护者设备上签名构建；上传对象存储；灰度发布；需要存档时运行 `gh release upload v1.3.0 <文件>` |

### 10.15 线上紧急修复

先按[第 14 章](#14-线上故障处理)止损。能回滚就先回滚，再修复。

**情况 A：`main` 上没有未发布的改动**

走正常的短流程：从 `main` 建 `hotfix/987-pay-callback`，只修复当前问题，加急审查，合并后打修订版本标签并部署。

**情况 B：`main` 上已经有未发布的改动**

从线上版本的标签修复，避免把未验证的功能一起带上线：

```bash
# 1. 从线上版本创建发布分支（pre-push hook 允许新建发布分支）
git fetch origin --tags
git switch -c release/1.2.x v1.2.0
git push

# 2. 创建修复分支
git switch -c hotfix/987-pay-callback
# 修复问题，补充测试
git add <改动的文件>
git commit -m "fix(pay): 修复支付回调重复处理"
git push

# 3. 向发布分支提 PR，加急审查后合并
gh pr create --base release/1.2.x \
  --title "fix(pay): 修复支付回调重复处理" \
  --body "Refs #987"
gh pr merge --squash --delete-branch

# 4. 打标签、发布并部署
git switch release/1.2.x
git pull
git tag -a v1.2.1 -m "v1.2.1"
git push origin v1.2.1
gh release create v1.2.1 --verify-tag --notes "修复支付回调重复处理（#987）"
```

**发布后必须把修复合回 `main`，否则下次发布时问题会再次出现：**

```bash
git fetch origin
git switch -c fix/987-port-to-main origin/main
git cherry-pick -x <发布分支上的修复提交>
git push
gh pr create --base main \
  --title "fix(pay): 修复支付回调重复处理" \
  --body "Closes #987"
```

GitHub 只有在 PR 合并到默认分支时才会自动关闭 Issue，所以 `Closes #987` 写在合回 `main` 的 PR 中。

### 10.16 回滚

**第 1 步：恢复线上服务。** 在服务器上部署上一个版本：

```bash
ssh deploy@<服务器>
cd /srv/client-acme-portal
./deploy.sh v1.2.0
```

如果出问题的版本包含不兼容的数据库迁移，不能直接回退代码，要先按 [13.4](#134-数据库变更) 判断。

**第 2 步：撤销 `main` 上的问题提交。** 否则下次发布时问题会再次出现：

```bash
gh pr revert 456
```

也可以在已合并 PR 的页面点击 Revert 按钮，或者手工操作：

```bash
git fetch origin
git switch -c revert/456-doc-upload origin/main
git revert <main 上的提交 SHA>
git push
gh pr create --base main --title "revert: 撤销文档上传功能" --body "原因和 Issue 链接"
```

**规则：**

- 不用 `git reset` 加强推来“回滚”共享分支。
- revert 同样走 PR 和 CI，紧急时加急审查。
- 修复后要重新上线时，另开新的 PR。

### 10.17 误操作急救

| 情况 | 操作 |
|---|---|
| 最后一次提交的信息写错，还没推送 | `git commit --amend -m "新信息"` |
| 撤销最后一次提交，但保留改动 | `git reset --soft HEAD~1` |
| 取消暂存某个文件 | `git restore --staged <文件>` |
| 丢弃某个文件未提交的改动 | `git restore <文件>`（无法恢复，先确认） |
| 改到一半要切换任务 | `git stash push -u -m "说明"`，回来后 `git stash pop`；长期并行用 worktree |
| rebase 中途乱了 | `git rebase --abort` |
| reset 或 rebase 后找不到提交 | `git reflog` 找到提交，再 `git switch -c rescue <SHA>` |
| 最后一次提交误带了大文件，还没推送 | `git rm --cached <文件>`，加进 `.gitignore`，`git add .gitignore`，再 `git commit --amend --no-edit` |
| 把密钥推送到了远程 | 立即轮换密钥，通知技术负责人，按 [14.5](#145-安全事件) 处理，之后再评估是否清理历史 |
| 不小心在本地 `main` 上提交了 | 见下方 |

pre-commit hook 会阻止在 `main` 上提交。如果用了 `--no-verify` 或 hook 没启用，而且还没有推送：

```bash
git branch feat/123-doc-upload   # 用当前内容建新分支
git reset --hard origin/main     # 把本地 main 恢复成远程的状态
git switch feat/123-doc-upload
```

`git reset --hard` 会丢弃未提交的改动，先用 `git status` 确认。

已经推送到远程的 `main`：不要强推覆盖，通知技术负责人，按 `main` 守卫的核查流程处理。

### 10.19 结项和交接

**先确认交付方式：**

| 方式 | 操作 | 适用情况 |
|---|---|---|
| 转移仓库 | 把仓库转给客户的账号或组织 | 合同约定交付完整历史，而且历史中没有不应交付的内容 |
| 交付新仓库 | 在客户仓库中提交清理后的当前代码 | 历史中有内部讨论、AI 记录或不应交付的内容 |
| 只交付安装包 | 交付发布包和文档 | 合同不交付源代码 |

**交付前检查：**

```bash
git ls-files | grep -E '\.env$|\.pem$|\.key$'   # 不应列出真实的密钥文件
git ls-files .trellis openspec                  # 检查要交付的 AI 规范和记录
```

再运行一次覆盖完整历史的密钥扫描，并按 [5.11](#511-结项与复盘) 的清单确认。

**收尾：**

```bash
gh repo archive TIanle-art/client-acme-portal   # 确认不再开发后归档
```

归档前关闭或转移未完成的 Issue 和 PR，移除外部协作者和部署密钥，把项目的密钥轮换或转交给客户。

### 10.20 转到组织

出现以下任一情况时，把仓库转到免费组织：同时有两个以上项目在开发，需要按人设置不同权限，或有外包和客户人员需要访问部分仓库。

1. 创建 GitHub Organization，选择免费计划。
2. 在组织中创建团队，比如 `developers`、`tech-leads`。
3. 在仓库的 Settings → General → Danger Zone 中，把仓库转移到组织。
4. 给团队分配仓库权限：普通开发者用 Write，技术负责人用 Maintain，外部人员只给需要的仓库。
5. 每位成员更新远程地址：

   ```bash
   git remote set-url origin git@github.com:<组织名>/<仓库名>.git
   ```

6. 更新 CI 中引用 `ci-workflows` 的地址。

转移后，Issue、PR、提交历史和仓库 Secret 都会保留，旧地址会自动跳转。私有包可能需要另外处理。

**免费组织的私有仓库仍然没有分支保护。** 需要强制保护时，开通 GitHub Team，然后按 GitHub 文档为 `main` 和 `release/*` 配置规则集：要求 PR、至少 1 人批准、CODEOWNERS 审查、CI 通过，禁止强推和删除。

## 11. 代码审查

### 11.1 审查时限

| 情况 | 首次响应 | 目标完成 |
|---|---|---|
| 普通 PR | 4 个工作小时内 | 1 个工作日内 |
| L3 PR | 4 个工作小时内 | 按风险确定，不因赶时间放松要求 |
| 紧急修复 | 立即 | 尽快，事后可以再复查 |

每天固定一到两个时间段集中审查。超过时限没人回应时，作者在团队频道提醒，技术负责人负责协调。

### 11.2 审查人怎么定

- 作者在 PR 中手动指定，通常是相关模块的负责人。
- L3 改动必须请技术负责人审查。
- 负责人不在时，请他的备份审查。
- 免费计划的私有仓库中 CODEOWNERS 不会自动请求审查，所以每个 PR 都要手动指定。

### 11.3 审查清单

**需求**
- [ ] 满足验收标准
- [ ] 没有实现范围外的功能
- [ ] 错误场景和边界情况符合规格

**设计**
- [ ] 符合现有的架构和分层
- [ ] 没有重复实现已有的功能
- [ ] 没有引入不必要的依赖或抽象
- [ ] 接口兼容旧版本客户端

**安全和数据**
- [ ] 权限校验在服务端执行
- [ ] 有未授权和跨租户的测试（如适用）
- [ ] 没有密钥、敏感日志或多余的数据外发
- [ ] 输入已校验，外部内容被当作不可信数据
- [ ] 模型调用有限额，用户取消后会停止上游请求（如适用）

**可靠性**
- [ ] 失败时不会静默吞掉错误
- [ ] 外部调用有超时，重试不会造成重复扣费或重复内容
- [ ] 支付、回调和后台任务具有幂等性
- [ ] 数据库迁移可以安全执行，有回滚或恢复方案

**测试**
- [ ] 测试验证的是业务行为
- [ ] 没有无故删除、跳过或放宽测试
- [ ] 测试失败时能指出真实问题

**可维护性**
- [ ] 命名和结构容易理解
- [ ] 复杂的决定有注释或 ADR
- [ ] 文档、规格和规范已同步

### 11.4 审查意见的写法

给意见加上前缀，让作者知道优先级：

| 前缀 | 含义 | 是否阻止合并 |
|---|---|---|
| `blocking:` | 必须修改 | 是 |
| `suggestion:` | 建议修改，作者可以决定 | 否 |
| `question:` | 想了解原因 | 不一定 |
| `nit:` | 小问题 | 否 |
| `praise:` | 值得肯定 | 否 |

```text
blocking: 这里没有校验 org_id，其他组织的成员也能访问这份文档。
请补上权限校验和跨组织访问测试。

suggestion: 这段重试逻辑可以复用 ai_gateway 中的封装。
```

审查针对代码，不针对人。也不要用“这是 AI 写的”作为质量差的理由。

### 11.5 AI 辅助审查

AI 审查可以放进 CI，也可以由作者主动运行，用来发现常见缺陷、遗漏的边界条件、安全问题、与规范不一致的地方和缺失的测试。

- AI 的意见由人判断，不必全部采纳，也不能当作已经审查过。
- 人工审查重点放在 AI 不擅长的地方：是否解决了正确的问题、架构取舍和业务规则。
- 作者和审查者都可以用 AI，但不能用它代替自己看 diff。

### 11.6 发生分歧时

1. 先在 PR 中讨论，说清楚理由和影响。
2. 超过两轮仍未解决，改为语音或当面讨论 10 到 15 分钟。
3. 还是无法决定时：模块问题由模块负责人决定，架构问题由技术负责人决定，业务问题由项目负责人决定。
4. 重要的决定写进 ADR。

## 12. 测试与验收

### 12.1 环境

| 环境 | 用途 | 数据 | 谁能部署 |
|---|---|---|---|
| 本地 | 开发和单元测试 | 模拟数据 | 开发者 |
| 测试 | 联调和验收 | 脱敏数据或模拟数据 | `main` 合并后自动部署 |
| 生产 | 真实用户 | 真实数据 | 技术负责人及其备份 |

测试环境和生产环境不共用数据库、模型密钥和第三方账号。测试环境不放在生产服务器上，可以用一台低配的服务器，或者按需启动、用完释放。

### 12.2 测试分工

| 层级 | 内容 | 谁负责 | 什么时候运行 |
|---|---|---|---|
| 静态检查 | lint、类型 | CI | 每个 PR |
| 单元测试 | 业务规则、工具函数 | 开发者 | 每个 PR |
| 接口测试 | 权限、校验、错误 | 开发者 | 每个 PR |
| 端到端测试 | 登录和核心流程 | 开发者 | PR 或合并后 |
| AI 评估 | 固定场景的结果质量 | 开发者 | 改提示词、模型或检索方式时 |
| 手工验收 | 体验、真机、安装和升级 | 项目负责人 | 发布前 |

不设统一的覆盖率数字，优先保证权限、计费、数据隔离和核心流程。AI 生成的测试也要审查，防止它只是重复了现有实现，或者为了通过而修改断言。

### 12.3 各端的验收重点

**网页和 SaaS**

- 主流浏览器和常见屏幕尺寸
- 登录过期、无权限和网络错误
- 组织切换和数据隔离

**微信小程序**

- 真机验证，至少覆盖 iOS 和 Android
- 用真实配置验证登录、支付和订阅消息
- 流式输出在真机上的表现
- 分包和包体积
- 隐私授权、类目和审核要求

**桌面软件（Windows、macOS、Linux 分别验证）**

- 全新安装、覆盖升级和卸载
- 旧版本数据迁移，迁移前自动备份
- 自动更新、更新失败和网络中断
- 离线规则
- 不同系统权限和杀毒软件环境
- Linux 没有密钥环时的提示

**AI 功能**

- 固定评估集没有明显退化
- 模型超时、限流和服务不可用时有明确提示
- 用户中途取消后停止生成
- 限额和成本统计正确
- 对提示词注入和超出范围的提问有防护

### 12.4 缺陷分级

| 级别 | 定义 | 示例 | 处理要求 |
|---|---|---|---|
| S0 致命 | 核心功能不可用、数据丢失、安全漏洞 | 无法登录、跨租户数据泄露 | 立即处理，阻止发布 |
| S1 严重 | 主要功能出错，没有可接受的替代办法 | 支付后状态不更新 | 发布前修复 |
| S2 一般 | 有替代办法，或影响范围小 | 某个筛选条件失效 | 决定修复或延期 |
| S3 轻微 | 体验或文案问题 | 错别字 | 排期处理 |

缺陷记录要写清：版本、环境、复现步骤、预期结果、实际结果，以及日志或截图。

修复缺陷时，先写一个能复现问题的测试，再修复。这样既能确认修对了，也能防止问题复发。

### 12.5 客户验收

```text
提交验收版本 → 客户按验收标准测试 → 记录问题 → 判断是缺陷还是变更
→ 修复，或走变更流程 → 回归验证 → 书面确认
```

验收期限和超期未反馈的处理方式，要提前写进合同。新增的要求属于需求变更，不算缺陷，见 [15.4](#154-客户需求变更)。

## 13. 发布与回滚

### 13.1 发布原则

- 通过 CI 构建，不在服务器上手工改代码。
- 每个版本都能追溯到具体的提交。
- 发布前先备份；L3 发布要有人值守。
- 避开客户的业务高峰；没有人能响应时，不做高风险发布。
- 小步频繁发布，比长时间攒一个大版本更安全。

### 13.2 版本号

- 桌面软件和公共库使用语义化版本：`主版本.次版本.修订号`。
- 后端使用 Git 标签，镜像标签同时带版本号和提交哈希。
- 小程序的版本号与 Release 记录对应。

具体的打标签命令见 [10.14](#1014-发布版本)。

### 13.3 后端和网页

```text
PR 合并 → CI 测试并部署测试环境 → 验收
→ 技术负责人打标签 → CI 构建镜像
→ 维护者在服务器上运行 deploy.sh：备份、拉取镜像、迁移、启动、健康检查
→ 验证核心流程 → 观察
```

观察错误率、延迟、资源占用和模型调用的失败率。L3 发布至少观察 30 分钟。

### 13.4 数据库变更

破坏性的变更分步发布，也就是“扩展 → 迁移 → 收缩”。以重命名字段为例：

| 步骤 | 操作 | 能否回滚 |
|---|---|---|
| 1 扩展 | 新增字段，新代码同时写新旧两个字段 | 回退代码即可，新字段保留 |
| 2 迁移 | 分批把旧数据复制到新字段，并核对 | 新字段可以重新生成 |
| 3 切换 | 代码改为读取新字段 | 改回读取旧字段 |
| 4 收缩 | 确认稳定后删除旧字段 | 只能依靠备份 |

**规则：**

- 高风险迁移不和大功能放在同一次发布。
- 大表变更先评估锁表时间。
- 迁移先在测试环境用接近真实规模的数据演练。
- 第 4 步单独发布。这一步才真正不可逆，要先确认备份可用。
- 不让 AI 直接在生产环境执行迁移。

`deploy.sh` 在健康检查失败时只回退代码，不回退数据库。所以每次迁移都要保证旧版本的代码也能在新的数据库结构上运行。

### 13.5 小程序

```text
开发版 → 体验版真机验证 → 提交审核 → 审核通过 → 发布
                                    └─ 按后台能力选择灰度发布
```

- 后端先发布，并兼容旧版小程序。
- 审核时间不完全可控，不要把发布安排在截止日当天。
- 服务器域名、隐私说明和类目资质提前确认。
- 回退和灰度能力以微信后台当前的功能为准，并提前演练。

### 13.6 桌面软件

```text
用 PR 更新版本号 → 打标签 → CI 构建三个平台的测试版本
→ 维护者设备上签名构建 → 打包检查 → 上传 Source Map
→ 上传对象存储 → 内部测试 → 灰度 → 观察崩溃和错误 → 全量
```

- 用户更新有延迟，后端要兼容旧版本客户端。
- 灰度比例逐步放大，例如 5%、20%、50%、100%，按用户量调整。
- 本地数据迁移前自动备份，并测试从多个旧版本升级。
- 有问题的版本立即停止推送，通过发布更高版本的修复包来回滚。
- 签名凭据只在维护者的设备上，不放进 GitHub。

### 13.7 回滚决策

出现以下任一情况，优先回滚，而不是在线上继续尝试修复：

- 核心流程不可用
- 错误率明显上升，原因不清楚
- 出现数据错误或安全问题
- 在约定时间内无法定位根因

| 场景 | 回滚方式 |
|---|---|
| 后端 | 在服务器上运行 `./deploy.sh <上一个版本>` |
| 网页 | 部署上一个版本的静态文件 |
| 数据库 | 优先用兼容的前向修复；确认影响范围后，才从备份恢复 |
| 小程序 | 按后台能力回退；不能回退时，修复后加急提审，同时让后端兼容 |
| 桌面软件 | 停止推送，发布更高版本的修复包 |
| 模型或提示词 | 切回上一版配置 |

每次 L3 发布前，都写明回滚方式，以及由谁决定、谁执行。Git 层面的操作见 [10.16](#1016-回滚)。

## 14. 线上故障处理

### 14.1 故障分级

| 级别 | 定义 | 响应目标 | 通报 |
|---|---|---|---|
| P0 | 服务不可用，数据丢失或泄露，支付严重出错 | 工作时间 15 分钟内 | 立即通知负责人和受影响的客户 |
| P1 | 核心功能严重受损，没有替代办法 | 工作时间 30 分钟内 | 通知负责人，必要时通知客户 |
| P2 | 部分功能异常，有替代办法 | 当天处理 | 团队内部 |
| P3 | 轻微问题 | 排期处理 | 记录即可 |

工作时间以外的响应要求，按合同和实际的值班安排确定。不承诺团队做不到的响应时间。

### 14.2 分工

| 角色 | 职责 |
|---|---|
| 指挥者 | 判断级别，分配任务，决定是否回滚。默认是技术负责人 |
| 处理者 | 排查和修复 |
| 沟通者 | 对内对外同步进度。默认是项目负责人 |

小团队可以兼任，但不能所有人都去查问题，却没有人和客户沟通。

### 14.3 处理流程

```text
发现 → 判断级别 → 拉人处理 → 止损（回滚、关闭功能、限流）
→ 定位根因 → 修复 → 验证恢复 → 通报 → 复盘
```

**先止损，再查根因。** 能回滚就先回滚，能关闭功能就先关闭。

处理过程中，在一个固定的地方记录时间线，方便交接和复盘：

```text
10:02 告警：登录接口 5xx 明显上升
10:05 判定为 P1，技术负责人指挥
10:12 确认与 10:00 的发布有关，决定回滚
10:18 回滚完成，错误率恢复正常
```

### 14.4 紧急修复

```text
1. 从线上运行的版本创建 hotfix 分支
2. 只修复当前问题，不夹带其他改动
3. 运行关键检查，请一位审查人加急审查
4. 发布并验证
5. 把修复合回 main，补充测试
6. 补写 Issue、发布记录和复盘
```

可以缩短的是等待时间，不能省略的是：可追溯的记录、基本的验证和第二个人的确认。除非所有人都联系不上而且影响严重，否则不绕过审查；绕过时事后补审。具体命令见 [10.15](#1015-线上紧急修复)。

### 14.5 安全事件

发现密钥泄露、未授权访问或数据泄露时：

1. 立即通知技术负责人。
2. 轮换相关密钥，吊销令牌，堵住入口。
3. 保留日志和证据，不要清除记录。
4. 评估受影响的数据和用户。
5. 涉及个人信息或客户数据时，立即请法务确认通知义务和时限，并通知客户。
6. 修复后写复盘。

### 14.6 AI 相关故障

| 情况 | 处理方式 |
|---|---|
| 模型服务不可用 | 切换到备用服务商，或者降级并明确提示用户 |
| 费用异常上升 | 触发限额，定位来源，必要时暂停功能 |
| 输出有害或错误的内容 | 回退提示词或模型，加强过滤，补充评估用例 |
| 提示词注入导致越权 | 关闭相关的工具权限，按安全事件处理 |
| 模型更新导致效果下降 | 切回之前的模型版本，运行评估，锁定版本 |

### 14.7 复盘

P0 和 P1 必须复盘，P2 按需复盘。复盘不追究个人责任，重点是找出系统为什么让这个错误发生并到达线上。使用[故障复盘模板](#219-故障复盘)，每个行动项都要有负责人和截止日期。

## 15. 沟通、决策与需求变更

### 15.1 信息放在哪里

| 内容 | 位置 |
|---|---|
| 任务和进度 | GitHub Issues、Projects |
| 代码讨论 | PR |
| 业务发现 | `docs/discovery/` |
| 需求 | `docs/prd/` 或 `openspec/` |
| 技术决定 | `docs/adr/` |
| 团队规范 | `handbook` 仓库、`.trellis/spec` |
| 发布记录 | GitHub Release、`docs/releases/` |
| 运维手册 | `docs/runbooks/` |
| 即时沟通 | 团队聊天工具，得出的结论写回上面的位置 |

**聊天中做的决定，不写回去就不算数。**

### 15.2 决策权

| 决定 | 由谁决定 | 记录在哪里 |
|---|---|---|
| 做什么、优先级、是否验收 | 项目负责人 | PRD、Issue |
| 业务规则是否正确 | 业务拍板人 | PRD、OpenSpec |
| 架构和技术选型 | 技术负责人 | ADR |
| 任务内的实现细节 | 开发者 | PR |
| 是否上线、是否回滚 | 技术负责人 | 发布记录 |
| 公共模板、规范和 Skill | 模板负责人 | 模板的 CHANGELOG |
| 跨项目的资源冲突 | 公司负责人 | 决策记录 |

### 15.3 问题升级

```text
成员自己解决（30 分钟到半天，看紧急程度）
    ↓
模块负责人
    ↓
技术负责人（技术问题）或项目负责人（业务问题）
    ↓
公司负责人（资源问题或重大风险）
```

进度有风险时，在迭代中途就说，不要等到截止日。

### 15.4 客户需求变更

```text
客户提出 → 记录 → 判断是缺陷还是变更
→ 评估范围、时间、费用和风险 → 客户书面确认
→ 更新 PRD 或 OpenSpec 和计划 → 进入开发
```

- 不符合已确认的验收标准：**缺陷**，按质保或合同处理。
- 超出已确认的范围：**变更**，走变更流程，使用[变更单](#2110-需求变更单)。
- 拿不准时，由项目负责人根据合同和需求文档判断，必要时和客户澄清。

AI 提高了开发速度，但变更仍然要评估。一个“很小的改动”也可能影响权限、测试和发布。

客户直接联系开发者时，开发者把需求转给项目负责人，不私下答应，也不直接修改。

### 15.5 对客户的状态同步

每周发一次[周报](#2111-客户周报)，内容包括：本周完成的内容和可以查看的版本、下周计划、风险和需要客户配合的事项、需要客户确认的决定和期限。

## 16. 客户项目与商务

### 16.1 立项前确认的条款

以下内容写进合同，具体措辞由法务确认：

- [ ] 范围、里程碑和验收标准
- [ ] 验收期限，以及超期未反馈如何处理
- [ ] 需求变更的流程和费用
- [ ] 代码和文档的归属，公司的通用模板和组件能否继续复用
- [ ] 客户的代码和数据能否发给 AI 工具，可以使用哪些工具和模型服务商
- [ ] 数据存放的地点和合规要求
- [ ] 模型 API 的费用由谁承担，用量超限怎么办
- [ ] 服务器、域名、备案、证书和第三方账号归谁
- [ ] AI 输出的准确性限制，以及人工确认的责任
- [ ] 质保范围、服务时间和维护费用

### 16.2 成本与报价

AI 产品除了开发成本，还有持续的模型成本。报价前至少测算：

| 项目 | 示例 |
|---|---|
| 单次任务成本 | 生成一份标书平均消耗多少 token |
| 单用户成本 | 每月的平均用量和最高用量 |
| 基础设施 | 服务器、存储、CDN、监控 |
| 第三方服务 | 证书、短信、邮件、支付 |
| 人工成本 | 开发、审查、维护和客户支持 |

先用评估集和试点用户测出真实数据，再确定报价和套餐。

### 16.3 交付物

- 源代码，以及构建和部署说明
- 环境变量说明（不含真实值）
- 数据库结构和迁移
- 系统架构说明
- 管理员和用户手册（按需）
- 测试和验收记录
- 第三方账号和依赖清单
- 运维和故障处理手册

交付方式和交付前检查见 [10.19](#1019-结项和交接)。

### 16.4 自研产品的授权

公司自己的产品（尤其是桌面软件）还要确定：

- 按账号、设备还是企业收费？
- 离线可以使用多久？
- 到期后，用户能否继续导出数据？
- 授权和会员状态都由服务器判定，本地判断只控制界面。

## 17. 合规与公司资产

本章是核查清单。具体是否适用，取决于产品和用户，上线前请法务或合规顾问确认。

### 17.1 数据分级

| 级别 | 示例 | 能否发给 AI 开发工具 | 能否进测试环境 |
|---|---|---|---|
| 公开 | 产品文档、公开的代码 | 可以 | 可以 |
| 内部 | 内部代码、架构文档 | 只限公司批准的工具 | 可以 |
| 客户保密 | 招标文件、标书、客户代码 | 需要合同或客户授权 | 脱敏后才可以 |
| 高敏感 | 密钥、身份证件、未脱敏的个人信息 | 不可以 | 不可以 |

每个项目立项时写清：有哪些数据，存在哪里，发给哪些服务，保存多久，谁能访问，怎么删除。

### 17.2 客户文件的处理

以标书类项目为例：

- 上传的文件加密存储，按组织隔离。
- 明确文件和生成结果的保存期限，并提供删除功能。
- 日志不记录文档正文。
- 只把必要的内容发给模型。
- 确认模型服务商的数据保留和训练政策。
- 客户数据不用于其他客户的模型调优或提示词示例，除非合同明确允许。
- 测试和评估样本必须脱敏，并限制访问范围。

### 17.3 生成式 AI 服务

公开信息显示：

- 面向公众提供的生成式 AI 服务，按规定备案。
- 通过 API 直接调用已备案模型的应用或功能，由地方网信办登记。
- 已上线的应用或功能，要在显著位置或产品详情页公示所使用的模型、备案号或上线编号。

要确认的问题：

- [ ] 产品是否面向境内公众？企业内部使用、面向企业客户分别如何认定？
- [ ] 使用的模型是否已备案？是否需要办理地方登记？
- [ ] 产品页面如何公示模型和备案信息？

### 17.4 AI 生成内容标识

《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行，涉及显式标识和文件元数据中的隐式标识。

- [ ] 文本、图片、音频、视频分别如何标识？
- [ ] 导出的 Word、PDF 是否需要写入标识或元数据？
- [ ] 用户需要不带显式标识的内容时，产品如何处理？
- [ ] 标书这类要提交给第三方的文件，如何兼顾标识要求和文件格式要求？

### 17.5 网站、小程序和应用备案

- [ ] **网站：** 确认域名和 ICP 备案。
- [ ] **小程序：** 完成小程序备案，确认服务类目和所需资质。
- [ ] **移动应用（以后如果要做）：** 工信部要求 App 主办者履行备案手续，未备案不得提供互联网信息服务。
- [ ] **桌面软件：** 确认下载网站、分发渠道和隐私说明。

### 17.6 个人信息和数据出境

- [ ] 隐私政策说明收集哪些信息、发给谁、保存多久。
- [ ] 提供查询、更正和删除的渠道。
- [ ] 使用境外的模型 API 或服务时，评估数据出境要求。《个人信息出境认证办法》自 2026 年 1 月 1 日起施行，适用哪条路径要由专业人士判断。
- [ ] 与客户、模型服务商的数据处理责任写进合同。
- [ ] 个人信息泄露时，明确通知流程和责任人。

## 18. 上线后的运营

### 18.1 用户支持

上线前确定：

- 用户从哪里反馈问题，比如客服微信、邮箱或应用内入口。
- 谁负责接收，多久回复。
- 如何把用户反馈转成 GitHub Issue。
- 如何收集版本号、日志和 `request_id`，而不要求用户发送敏感文件。
- 哪些问题要升级给技术负责人。

### 18.2 监控和告警

早期保持轻量，具体配置见《公司项目脚手架规范》13.8 节。告警要发给明确的人，并写清工作时间以外是否响应。

### 18.3 AI 功能的观测

- 记录每次调用的功能、模型、token、成本、耗时和错误码，默认不记录完整的用户内容。
- 以下情况要告警：模型错误率上升、单个用户或项目费用异常、响应明显变慢、用户大量重试或取消。
- 在 AI 结果旁边提供简单的“有帮助/有问题”入口。收集反馈前，明确是否保存用户内容。
- 用户反馈的错误结果，补进评估集。

### 18.4 备份和恢复

- 数据库每天自动备份到服务器以外的地方。
- 每季度至少做一次恢复演练。
- 写清恢复步骤和负责人。
- 定好可接受的数据丢失时间和恢复时间，按实际能力写进合同。

### 18.5 上线前要准备的文档

- 用户手册和常见问题
- 更新日志
- 隐私政策和用户协议
- 运维手册：部署、回滚、备份恢复和常见故障
- 第三方许可证声明

## 20. 度量与持续改进

### 20.1 关注的指标

每两周看一次，用来发现流程问题，不用来考核个人。

| 指标 | 说明 | 变差时检查 |
|---|---|---|
| 需求交付周期 | 从开始开发到上线 | 任务是否太大，审查是否堵塞 |
| PR 首次响应时长 | 审查是否及时 | 审查人是否太少，PR 是否太多 |
| PR 大小 | 是否容易审查 | 任务拆分和 AI 的改动范围 |
| 返工次数 | 需求是否清楚 | 业务发现和验收标准的质量 |
| CI 首次通过率 | 自检和规范情况 | AI 是否运行了检查 |
| `main` 守卫告警次数 | 约定是否被遵守 | Git hook 是否启用，流程是否太繁琐 |
| 上线缺陷数 | 质量门禁是否有效 | 测试和审查的盲区 |
| 故障恢复时长 | 回滚和监控能力 | 回滚流程和告警 |
| 估算偏差 | 排期是否可靠 | 是否低估了审查、测试和外部依赖 |
| AI 工具成本 | 投入是否合理 | 模型选择和无人看管的运行 |

代码行数和 AI 生成比例不适合作为效率指标。它们很容易上升，却不代表交付了更多价值。

### 20.2 如何改进流程

- 每次复盘最多选 3 个改进项，每项都有负责人和截止日期。
- 流程的改动通过 PR 修改 `handbook` 仓库，让团队可以讨论。
- 新规则先试行一个迭代，没有效果就删掉。
- 定期删除没人遵守的规则，这比不断增加规则更重要。

## 22. 完整示例

下面用一个虚构的例子，展示一个 AI 功能如何走完整个流程。

**需求：** 智能标书项目中，客户希望自动提取招标文件中的废标条款。

**团队：** 小陈（项目负责人）、老王（技术负责人）、小李（后端，使用 Claude Code）、小赵（前端，使用 Cursor）、刘经理（客户方的业务拍板人，做过多年投标）。

### 22.1 判断流程

| 维度 | 判断 |
|---|---|
| 工作类型 | 功能开发 |
| 规模 | 复杂业务：规则多、容易有争议 |
| 风险 | L2；涉及数据库迁移的任务为 L3 |
| 后端 | FastAPI（AI 文档处理是核心功能） |
| 流程 | 业务发现 + OpenSpec + 评估集 |

### 22.2 业务发现

小陈和刘经理一起看了 8 份脱敏的招标文件，又跟着投标人员走了一遍流程，发现：

- 废标条款分散在多个章节，有些写法很模糊。
- 漏掉一条就可能导致废标，所以“漏提”比“多提”严重得多。
- 刘经理要求：AI 不能自己判断含糊的条款，必须标出来让人确认。

成功标准定为：8 份样本中明确的废标条款漏提为 0，每条都标出原文页码。

### 22.3 规格

小李在 AI 对话框运行 `/opsx:explore`，让 AI 只列出不明确的问题。其中“条款写法含糊时算不算废标项”由刘经理回答：标记为“需要人工判断”。

问题都关闭后，小李运行 `/opsx:propose add-disqualification-extraction`，生成提案、场景、设计和任务。规格 PR 中，刘经理看场景，老王看设计，两人都确认后才开始实现。

### 22.4 拆任务

| Issue | 内容 | 负责人 | 依赖 | 风险 |
|---|---|---|---|---|
| #201 | 定义解析结果的接口契约 | 小李 | | L2 |
| #202 | 新增条款表和迁移 | 小李 | | L3 |
| #203 | 解析任务和废标条款提取 | 小李 | #201、#202 | L2 |
| #204 | 前端展示条款、页码和确认按钮 | 小赵 | #201 | L2 |
| #205 | 评估集和评估脚本 | 小李 | #203 | L2 |

#201 最先合并。之后小赵用生成的 TS 类型和模拟数据开发，不必等后端全部完成。

### 22.5 开发（以 #203 为例）

```bash
git fetch origin
git worktree add ../bid-203 -b feat/203-disqualification-extraction origin/main
cd ../bid-203
make setup
```

小李在新的 Claude Code 会话中，用任务指令模板交代了 Issue、OpenSpec 变更和规范，要求先出计划。AI 的计划中准备新写一个 PDF 解析函数，小李发现项目里已有一个，就要求复用。

实现过程中，AI 第一次写的测试只检查“返回了条款”。小李要求补充“含糊条款必须标记为需要人工判断”的测试，并故意删掉标记逻辑，确认测试会失败。

### 22.6 自检、PR 和审查

小李运行 `make check`，用两份样本走了一遍流程，然后看完整 diff。他发现 AI 顺手改了一个无关的日志格式，于是还原了。

PR 中写明：风险 L2，主要由 AI 生成的是解析服务和测试，请重点看页码定位和含糊条款的处理，审查人指定老王。

老王留下两条意见：

```text
blocking: 解析任务失败时，任务状态一直停在“处理中”，用户看不到原因。
请记录失败原因，并允许重试。

suggestion: 条款的序列化可以复用 example_items 中的写法。
```

小李修改后，CI 通过，老王批准。小李用 Squash Merge 合并，`main-guard` 检查通过，测试环境自动部署。

### 22.7 验收和发布

小陈和刘经理用 8 份样本逐条验收，发现一份扫描件的页码有偏差，记为 S2 缺陷，修复后回归通过。刘经理书面确认验收。

因为 #202 包含迁移，老王选在客户的业务低峰期发布：

```bash
git tag -a v1.4.0 -m "v1.4.0"
git push origin v1.4.0
gh release create v1.4.0 --verify-tag --generate-notes
# 镜像构建完成后
ssh deploy@<服务器>
cd /srv/bid-generator
./deploy.sh v1.4.0
```

### 22.8 归档和沉淀

小李运行 `/opsx:archive add-disqualification-extraction`，用 `git diff openspec/specs` 确认主规格已更新。复盘后形成 3 项改动：

1. `.trellis/spec/backend/` 增加“后台任务失败时必须记录原因，并允许重试”，附示例路径。
2. 扫描件的页码问题加入评估集。
3. 把“含糊条款必须交给人判断”的做法写进项目的 `AGENTS.md`。

## 23. 落地计划

时间按团队情况调整。不要一开始就全部铺开，先在一个真实项目上试行。

### 第 1 周：定人和规则

- [ ] 指定技术负责人、模板负责人，以及各自的备份
- [ ] 个人 GitHub 账号开启双因素认证，恢复码存进公司的密码管理工具
- [ ] 建立 AI 工具准入表和数据分级规则
- [ ] 整理公司资产清单
- [ ] 列出要咨询法务的问题
- [ ] 全员阅读两份规范

**完成标志：** 每个人都知道自己的角色、一个任务从开始到完成要经过哪些步骤，以及哪些数据不能发给 AI 工具。

### 第 2 周：搭公共基础

- [ ] 建立 `handbook`、`spec-templates`、`ci-workflows` 仓库
- [ ] 写好公共的 `AGENTS.md`、Git hook、公司 Skill 和同步脚本
- [ ] 在测试仓库验证 Git hook 和 `main` 守卫
- [ ] 在每种常用 Agent 上完成 [8.3](#83-ai-工具准入) 中的新 Agent 验证
- [ ] 每人完成一个小改动，走完 PR、CI 和审查

**完成标志：** 不同的 Agent 都能在同一套规则下完成任务，并通过 CI。

### 第一个真实项目

- [ ] 完成业务发现，确定第一期范围和成功标准
- [ ] 按《公司项目脚手架规范》选择技术组合，建这个项目需要的模板
- [ ] 用 OpenSpec 完成一个核心功能，建立评估集
- [ ] 走完测试、审查、验收、发布，并演练一次回滚和一次备份恢复
- [ ] 测算单次任务的模型成本
- [ ] 复盘，删除无效的流程，把验证过的内容提炼回模板

**完成标志：** 一个核心功能被业务拍板人验收，并且上线或可以上线。

### 以后

- 多个项目稳定后，再推广到所有项目。
- 出现 [10.20](#1020-转到组织) 中的情况时，转到组织。
- 多人同时跑很多 Agent 且开始混乱时，再评估 Agent 调度平台。

### 判断流程是否有效

运行一个月后，以下问题的答案都是“是”，就说明流程基本落地了：

- 任何人都能在 1 分钟内从看板上看到谁在做什么。
- 换一个人或一个 AI 会话，可以根据仓库内容接着工作。
- 大部分 PR 能在 1 个工作日内得到审查。
- `main` 守卫很少告警，告警后当天有人核查。
- 线上出问题时，知道谁负责，以及如何回滚。
- AI 的同一种错误不会反复出现。

## 24. 默认值与待决定事项

### 24.1 默认值

以下是起始建议，不是行业标准，按实际情况调整：

| 事项 | 默认值 | 需要调整的情况 |
|---|---|---|
| 迭代周期 | 1 周 | 需求稳定、任务较大时改为 2 周 |
| 单个任务大小 | 不超过 2 个工作日 | 探索性或难以拆分的任务 |
| 单个 PR 大小 | 不超过 400 行有效改动 | 迁移、生成代码等特殊情况 |
| 普通 PR 的批准人数 | 1 人 | 客户要求更严格时增加 |
| PR 首次响应 | 4 个工作小时 | 团队跨时区或人数很少时放宽 |
| 每人并行的 Agent 任务 | 2 到 3 个 | 根据审查能力调整 |
| 团队待审 PR 上限 | 人数 × 2 | 根据实际积压情况调整 |
| L3 发布的观察时间 | 不少于 30 分钟 | 根据风险和流量调整 |
| P0 响应 | 工作时间 15 分钟内 | 按合同和值班安排调整 |
| 指标回顾 | 每两周 | 项目少时改为每月 |
| 桌面灰度比例 | 5% → 20% → 50% → 100% | 用户量小时减少阶段 |
| 合并方式 | 只允许 Squash Merge | 确实需要保留完整提交历史时 |
| 离线授权有效期 | 7 天 | 按产品调整 |

### 24.2 待决定事项

| 事项 | 什么时候决定 | 由谁决定 |
|---|---|---|
| 技术负责人、模板负责人及备份 | 第 1 周 | 公司负责人 |
| 公司正式支持的 2 到 3 种 Agent | 第 2 周验证后 | 模板负责人 |
| 主用和备用的模型服务商 | 第一个 AI 项目立项时 | 技术负责人 |
| 各项目的后端选择 | 每个项目立项时 | 技术负责人 |
| 测试环境放在哪里 | 第一个项目上线前 | 技术负责人 |
| 工作时间以外是否响应故障 | 签第一个运维合同前 | 公司负责人 |
| Windows 和 Apple 签名证书 | 第一个桌面项目立项时 | 技术负责人 |
| 何时转到组织、是否开通 GitHub Team | 出现 [10.20](#1020-转到组织) 中的情况时 | 公司负责人 |
| 合规事项的适用范围 | 每个面向公众的产品上线前 | 公司负责人和法务 |
