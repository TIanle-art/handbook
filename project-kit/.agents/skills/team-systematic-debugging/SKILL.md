# 系统化调试

先找到根因，再修改代码。不要靠猜测反复尝试。

## 步骤

1. **复现问题**
   - 找到能稳定复现的最小步骤或测试。
   - 记录准确的错误信息、堆栈和相关日志，不要转述。
   - 无法复现时，先说明已尝试的方法，向人确认环境和步骤。

2. **收集事实**
   - 阅读出错位置附近的代码和最近的相关改动（`git log -p -- <文件>`）。
   - 查看输入数据、配置和环境变量是否与预期一致。
   - 区分“已确认的事实”和“推测”。

3. **提出一个可验证的假设**
   - 一次只验证一个假设，写清楚：如果假设成立，应该观察到什么。
   - 用最小的实验验证，比如加一条日志、写一个最小测试、缩小输入。

4. **修复根因**
   - 修改针对根因，而不是只让报错消失。
   - 不吞掉异常，不加无关的重试，不跳过、不放宽、不删除测试。
   - 改动只限于问题相关的文件。

5. **防止复发**
   - 先写一个能复现问题的测试，确认它在修复前失败，修复后通过。

6. **验证并报告**
   - 运行 `make check`，贴出真实的命令输出。
   - 报告：根因是什么、怎么修的、怎么验证的、还有什么风险。

## 停下来的条件

出现以下任一情况，停止修改，向人说明当前情况：

- 连续两次修复都没有解决问题。
- 发现问题来自需求不清、设计缺陷或外部服务。
- 修复需要改动登录、权限、支付、数据库迁移、CI 或生产配置。

说明时包括：复现步骤、已验证和已排除的假设、当前的判断和建议的下一步。
